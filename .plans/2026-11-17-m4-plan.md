## 1. What M4 adds

- **Four settings,** `enable-load-extension`, `defensive`, `dqs-dml` and `dqs-ddl`, each `#t` or
  `#f`, the last three set by one `sqlite3_db_config` call at open, held by the set's own answer
  (ADR-0021, decisions 1 to 3; ADR-0018, amended). The names are the maintainer's (Q14).
- **The opt-in, and a condition for a library without extension loading.**
  `(enable-load-extension . #t)` lets `load-extension!` work; `#f`, or no setting, makes it
  refuse, naming the fix (Q15). `&sqlite-extensions-unavailable` is raised by an open that opts in
  where `sqlite3_load_extension` is absent, as on Apple's library (ADR-0021, decisions 5 and 10;
  ADR-0013, amended).
- **`load-extension!`,** which takes an absolute path (Q16) and refuses a connection that didn't
  opt in before anything reaches C (ADR-0021, decisions 6 and 7).
- **Three entry points:** `sqlite3_db_config`, bound with `(__varargs_after 2)`, and
  `sqlite3_free`, both required and plain; `sqlite3_load_extension`, optional and
  `__collect_safe` (ADR-0021, decisions 4, 8 and 9; ADR-0002 and ADR-0011, amended). Each with its
  convention row, header check and decoy switch; the two required ones dealt by the pattern of
  five, the optional one outside it (§4.6).
- **Four constants,** the ops, checked against `sqlite3.h`.
- **`make check-variadic`,** run as a step of CI's `main` job, as chez-curl runs its own
  (ADR-0001, amended; §4.2).
- **FTS5 on CI's `current` lane,** and suites for FTS5 and JSON (ADR-0003, amended).
- **The public names, `docs/reference.md`, `test-public` and `test-reference`** for each: two new
  exports, `load-extension!` and `sqlite-extensions-unavailable?`, 70 names.

**Not in M4:** SQL's `load_extension()`, which stays refused; `sqlite3_enable_load_extension`;
`sqlite3_config`; `db_config`'s other ops and shapes; `TRUSTED_SCHEMA` as an op (pre-work Q7);
`sqlite3_auto_extension`; any callback into Scheme (brief §4). An extension's own functions are C
called by C, and are the extension's.

  verb refuses a connection that didn't opt in, before any C call. An open that doesn't opt in
  makes no `db_config` call, so the library's starting value (1 on Ubuntu's) is never reached:

  the guarantee lives."
- **Q4. Testing a library without extension loading: "The decoy"** (2026-11-16).
  "`DECOY_LACKS_sqlite3_load_extension`. A suite opens the decoy with the opt-in, asserts the named
  condition, and reads the call log to show that no `db_config` call was made. No real
  `OMIT_LOAD_EXTENSION` build." The log's no `db_config` can't fail on the decoy, whose open
  always fails first; §4.3 says what the log does show.
- **Q5. DQS's default: "SQLite's default, settable"** (2026-11-16). "Connections start with DQS
  on, as every library measured does. A caller turns `DQS_DML` and `DQS_DDL` off by name."
- **Q6. `DEFENSIVE` hides `writable_schema`: "Document it, with a row"** (2026-11-16). "The
  reference for `defensive` says a caller's `PRAGMA writable_schema = 1` does nothing under it. A
  row asserts that the set answers done and reads back 0, and is watched failing with defensive
  off."
- **Q7. `TRUSTED_SCHEMA`: "PRAGMA only"** (2026-11-16). "ADR-0018's `trusted-schema` stays the
  one way in to that flag. No `TRUSTED_SCHEMA` op: brief §2.8's three options stand."
- **Q8. The read-back: "Hold the set's answer"** (2026-11-16). "One call per set. The cell holds a
  sentinel before the call, the code is asserted, and a cell other than the value asked raises
  `&sqlite-setting-mismatch`."
- **Q9. The convention on Linux: "Check plus check-variadic"** (2026-11-16). "`test-conventions`
  asserts that the binding carries `(__varargs_after 2)` in the shape `(db op int int*)`. A
  `check-variadic` target removes it in a copy and watches that check fail, as chez-curl's does."
- **Q10. When a set runs: "In the settings list"** (2026-11-16). "The extension opt-in, `defensive`
  and the two DQS options join `open-database`'s settings list (ADR-0018) as new names, set at
  every open and checked by the set's own answer (Q8), with engine rows like M3 slice 5's."
  "Set at every open" is ADR-0018's "the list runs at every open": each open sets what its list
  names, and Q13 made that the rule, a setting set only where named. **For the opt-in, Q15's
  answer departs from it:** `(enable-load-extension . #f)` is named and makes no call, and only
  `#t` is a set (§3).
- **Q13. `DEFENSIVE`'s start differs by library: "Library's start, documented"** (2026-11-17).
  "`defensive` is set only where a caller names it in the settings list. The reference says
  Apple's library starts it on, so a caller who needs one behaviour everywhere names it. No call
  is added to an open."

**Settled here:**

- **Q2. A suite on a library without FTS5** follows Q1, as the pre-work said it would. The FTS5
  suite's first row holds `sqlite-compile-option? "ENABLE_FTS5"` to
  `select count(*) from pragma_module_list where name = 'fts5'`, either way, so a library whose
  option and module disagree fails by name (F1). Where both say yes, every FTS5 row runs. Where
  both say no, the suite prints `FTS5 unavailable`, as the memory check names itself unavailable
  (ADR-0005, amended), runs no FTS5 row, and asserts the refusal in their place: `create virtual
  table … using fts5` prepares, then raises `&sqlite-error`, code `error`, at its step, never
  checked by its message (F1; pre-work). So the suite runs on every lane: on `floor`, after Q1,
  it runs the refusal.
- **Q11. `sqlite3_db_config` is plain,** by ADR-0011's rule, now measured: under another
  connection's `BEGIN EXCLUSIVE` and write, with a 1500 ms busy timeout, every set of the four ops
  answered 0 in 0.001 ms or less, where a prepare there waited 1501 ms (D4). It takes the
  connection's mutex, which only the owning thread holds (ADR-0010; `sqlite3_interrupt` takes
  none).
- **Q12. The codes:** 0 is a set that took; any other raises `&sqlite-error` from the one
  procedure, as it raises every code, with no table of its own. Measured: 1 for an op the library
  doesn't know (pre-work), which can't happen at the floor, since all four ops are in 3.45.1's
  header and `test-constants` holds them there; and Apple's 21, for `ENABLE_LOAD_EXTENSION` alone,
  where Apple's other four ops answer 0 (pre-work's Mac step). Apple's library lacks
  `sqlite3_load_extension`, so the opt-in is refused before that call is made (§4.3).
  **The code is the call's own answer, never the connection's,** and the message `sqlite3_errstr`
  of it: `db_config` sets no error on its connection, whose extended code read 0 after a refused
  set on a fresh connection, and another statement's 1 after one (D3). M2's `failure-details`
  reads the connection's code, and `raise-sqlite-error` refuses a low byte of 0, 100 or 101 as no
  error: given D3's 0 it raised an assertion violation, `(not-an-error 0)`, where the call's 1
  gives `&sqlite-error` `error` (rv2). So neither M4 call goes through `failure-details`.

## 3. Questions for the maintainer

Three came from this plan. The maintainer settled all three on 2026-11-17, each the
recommendation. Each item below quotes the option picked.

### Q14. The new public names

M4 adds a verb, a setting that opts in to it, a condition's predicate, and three settings whose
names brief §2.8 and the pre-work already use: `defensive`, `dqs-dml`, `dqs-ddl`. Those three are
each their op's C name with `SQLITE_DBCONFIG_` dropped, lower-cased, `_` turned to `-`, the rule
ADR-0013 names codes by; by the same rule `TRUSTED_SCHEMA` would be `trusted-schema`, which is
already ADR-0018's PRAGMA for the same flag. M3's names were the maintainer's "Short names" (the M3
plan's Q1).

- **A. The rule's names:** the setting `enable-load-extension`, the verb `load-extension!`, the
  predicate `sqlite-extensions-unavailable?` (recommended).
- **B. A shorter opt-in:** the setting `extensions`, the verb `load-extension!`, the predicate
  `sqlite-extensions-unavailable?`.
- **C. The verb's name for both:** the setting `load-extension`, the verb `load-extension!`, the
  predicate `sqlite-no-extension-loading?`.

**Recommendation: A.** One rule names all four settings, so a reader finds each in SQLite's
documentation by its C name, as a code is found; `enable-` says what `#t` does. The verb is
`sqlite3_load_extension`'s name, `!` for its effect, as `interrupt-database!` has one.
**Evidence:** ADR-0013, decision 3; ADR-0021, decision 1; pre-work Q7.

**Answer: "The rule's names"** (the maintainer, 2026-11-17): `enable-load-extension`,
`load-extension!`, `sqlite-extensions-unavailable?`. Declined: `extensions`; `load-extension` and
`sqlite-no-extension-loading?`.

### Q15. What `(enable-load-extension . #f)` does

The opt-in is `#t`. A list can name the setting `#f` too: a caller computing it from
configuration will. Q3 settled that the guarantee is the verb's refusal in Scheme, and that "an
open that doesn't opt in makes no `db_config` call". Measured: Ubuntu's library starts the C call
at 1 and the rest at 0; Apple's library lacks the entry point and answers 21 to every call of the
op (pre-work; mac-d7). No other code in the process can reach a connection's handle (ADR-0012,
decision 2).

- **A. The same as leaving it out:** no `db_config` call, and `load-extension!` refused
  (recommended).
- **B. One more call:** the op set to 0 and held, as `defensive`'s `#f` is. On a library that
  lacks `sqlite3_load_extension`, no call, since Apple's would answer 21 and refuse the open.
- **C. Refused:** the setting's domain is `#t` alone, and `#f` an assertion violation before
  anything opens.

**Recommendation: A.** It keeps Q3's rule whole, and `#f` reads as "don't opt in". B's call
protects nothing the refusal doesn't, and needs a case for Apple's 21; C makes a computed `#f`
fail where it means what it says.
**Evidence:** pre-work Q3 and the Mac step; ADR-0021, decisions 5 and 6.

**Answer: "Same as leaving it out"** (the maintainer, 2026-11-17). Declined: a call setting the
op to 0; `#f` refused.

### Q16. What path `load-extension!` takes

SQLite hands the path to `dlopen`, then, when that fails, the path with a suffix appended: `.so`
on Linux, `.dylib` under `__APPLE__`, by 3.45.1's own `azEndings`. Measured on Linux, on all
three libraries:
- a bare name, `ext.so`, wasn't found though the working directory held it (L2); from another
  working directory, with `LD_LIBRARY_PATH` naming the directory that holds it, `ext.so` and
  `ext` both loaded, and neither without it (rv3). So `dlopen` searches its own list, the
  environment's among it, and never the working directory;
- `./ext.so`, a relative path, loaded, from the working directory (L2);
- `/…/ext`, an absolute path without the suffix, loaded `/…/ext.so` (L2).

On macOS, dlopen(3) documents that a leaf name is searched in `DYLD_LIBRARY_PATH`, the caller's
rpaths, then, for an unrestricted process, the working directory: documented, not measured here.
ADR-0002 rejected a bare soname for libsqlite3 itself, since it "lets `LD_LIBRARY_PATH` and
`DYLD_*` decide silently", and made `CHEZ_SQLITE3_LIBRARY` an absolute path, loaded as given.

- **A. An absolute path:** anything else an assertion violation before any C call, as the
  override's `invalid-override` is (recommended). SQLite's suffix still applies.
- **B. Any path holding a `/`:** `dlopen` never searches, and a relative path is the working
  directory's.
- **C. Any string, as SQLite takes it:** a bare name is `dlopen`'s search.

**Recommendation: A.** The process loads only the file the caller named, which the environment
can't redirect, as ADR-0002 has it for the library itself; a relative path depends on the
working directory at the call, which a long-lived program changes. A refused form can be
accepted later; an accepted one can't be withdrawn.
**Evidence:** L2; rv3; 3.45.1's `azEndings`; ADR-0002, decision 1 and Rejected.

**Answer: "An absolute path"** (the maintainer, 2026-11-17). Declined: any path holding a `/`; any
string.

### Q14 and Q15 together: the re-check

The plan's review found the two answers pull against each other: the setting is named for the C
op, whose 0 turns the C call off, yet under Q15 `#f` makes no call at all. Put to the maintainer
again, from the user's side, they confirmed it: **"Yes, as shown"** (2026-11-17).

The setting names what it does to the library's own verb, not the C flag. It mirrors Python's
`sqlite3`, whose `enable_load_extension(True)` comes before `load_extension(path)`: `#t` lets
`load-extension!` work; `#f`, or no setting, makes it refuse, and **the refusal's message names the
fix, `(enable-load-extension . #t)`.** The C op is how `#t` is done. The C flag's own state can't
be observed through the library: no verb reads it, and SQL's `load_extension()` stays refused
whatever it holds. The maintainer's principle is least surprise, and a clear method for a user to
load an extension. So `docs/reference.md`'s entry, owed by slice 4, carries a short example: open
with the setting, load by an absolute path, and the refusal without it (§4.8).

## 4. Decisions that bind every slice

Each cites its evidence, and is proposed in the record named.

### 4.1 The `db_config` settings (ADR-0021, decisions 1 to 3; ADR-0018, amended)

```scheme
(open-database "app.db" '((journal-mode . wal) (defensive . #t) (dqs-dml . #f) (dqs-ddl . #f)))
(call-with-database "plugins.db" '((enable-load-extension . #t))
  (lambda (db) (load-extension! db "/opt/app/lib/ext.so") …))
```

- **The table,** each value `#t` or `#f`, written as 1 or 0 to its op, its read-back the call's own
  cell:

  | Setting | Op | Starts at |
  |---|---|---|
  | `enable-load-extension` | `SQLITE_DBCONFIG_ENABLE_LOAD_EXTENSION`, 1005 | 0; 1 on Ubuntu's; Apple's answers 21 and leaves the cell |
  | `defensive` | `SQLITE_DBCONFIG_DEFENSIVE`, 1010 | 0; 1 on Apple's |
  | `dqs-dml` | `SQLITE_DBCONFIG_DQS_DML`, 1013 | 1 everywhere measured |
  | `dqs-ddl` | `SQLITE_DBCONFIG_DQS_DDL`, 1014 | 1 everywhere measured |

  The starts are the pre-work's census, seven libraries. `enable-load-extension`'s `#t` sets 1;
  its `#f` makes no call (Q15, §3).
- **Set only where named** (Q5, Q13): an open makes no call for a setting the list doesn't name.
- **One call, in a section of its own, held by its answer** (Q8): the cell, a counted `int`
  block, holds a sentinel that is neither 0 nor 1 before the call. Code 0 with the value written
  matches; code 0 with another cell raises `&sqlite-setting-mismatch` (the setting; `#t` or `#f`
  asked; `#t` or `#f` read, `()` for a cell left at the sentinel, any other integer as itself);
  another code raises `&sqlite-error` whose code and extended code are that answer, and whose
  message is `sqlite3_errstr`'s, never the connection's (Q12; D3; rv2). Either closes the
  connection first, and a close that fails then isn't raised over it (ADR-0018, decision 7,
  amended).
- **Where in the order:** ADR-0018's decision 5 unchanged. `busy-timeout` first, then the rest in
  the list's order, PRAGMAs and ops alike, each finished before the next begins. A set does no I/O
  and never waits (D4), so `busy-timeout`'s place neither helps nor hurts it. No op changes what a
  PRAGMA of the list does: on a file holding a table, every value of the six read back as written
  at the library's start and with `DEFENSIVE` 1 and both DQS 0, where `journal_mode = off` and
  `writable_schema = 1`, outside the list, were refused silently under `DEFENSIVE` (rv1, part C).
- **Under the open's claim** (ADR-0018, amended in M3 slice 5): each set is one more section, at
  the next position, claimed inside it. A run the call has passed is refused there, touching
  nothing. So each set is made once a call, by whichever run reaches it first. The cell's block
  lives whole in that section, as every C string under engines does (ADR-0011, amended).
- **At open, nothing is expired.** A set that changes a flag expires the connection's other
  statements, and one prepared under DQS on fails at its next step after DQS is turned off (D1,
  D2). At open the connection holds no statement: each PRAGMA's is finalized before the next
  setting begins, and the cache is empty. That is why the sets are at open, and only there
  (Q10; ADR-0018, decision 6).
- **Nothing else is needed at open:** each op round-trips on `:memory:`, a file whose schema
  isn't read, `READONLY`, `NOMUTEX`, inside a transaction and beside a held row (D5).
- **The complement:** every other `SQLITE_DBCONFIG_*` op of 3.45.1's and 3.54.1's headers, named
  by the rule, is `unknown-setting`; `trusted-schema` stays the PRAGMA (Q7).
- **The docs** (Q6, Q13): the four rows; each starts as its library does, and Apple's starts
  `defensive` on, so a caller who needs one behaviour everywhere names it; under `defensive`,
  `PRAGMA writable_schema = 1` answers done and does nothing; with `dqs-dml` or `dqs-ddl` off, a
  double-quoted name that isn't a column fails at prepare, and SQLite's message for it differs by
  version (pre-work).

### 4.2 The binding and its check (ADR-0021, decision 4; ADR-0001 and ADR-0011, amended)

- **One form,** literal at its use, as every binding is (ADR-0011's M1 slice 2 amendment):

  ```scheme
  (bind-required report
    (foreign-procedure (__varargs_after 2) "sqlite3_db_config" (uptr int int uptr) int))
  ```

- **The convention table gains `variadic`,** which `convention-of` reads from exactly
  `((__varargs_after 2))`. Anything else, `(__varargs_after 3)`, or `__collect_safe` beside it,
  reads as `(other …)` and mismatches. The row's prototype is `("int" ("sqlite3*" "int" "..."))`.
- **`test-constants` holds the prototype to the header** through `_Generic`, as `int (*)(sqlite3*,
  int, ...)`, and its map rule grows one case: a prototype ending `"..."` maps its named
  parameters to the row's leading arguments, its row's convention must be `variadic`, and the
  convention's 2 must be the count of named parameters. A row planted with 3, or with the variadic
  tail's types in the prototype, fails by name.
- **`make check-variadic`,** a Makefile target and `tests/check-variadic.sh`, in a copy of the
  tree:
  1. the control: the unchanged copy passes `test-conventions` and `test-native`;
  2. the mutant: `(__varargs_after 2)` stands in `native.sls` exactly once, is removed, stands
     nowhere after, and that one line alone has changed;
  3. `test-conventions` fails on it, its only failing tests those that read the variadic row, its
     violations exactly `((mismatch "sqlite3_db_config" convention variadic plain))`;
  4. on Apple arm64, by Chez's `(machine-type)`, `arm64osx` or `tarm64osx`, never `uname`,
     `test-native` runs on the mutant and must fail, by name or by dying; on any other machine its
     result is reported, never failed.

  chez-curl's `check-variadic` is the design: one use here, where chez-curl's template has seven,
  so its 480 lines aren't needed. None of its code is copied.
- **CI's `main` job runs `check-variadic`; `make test` doesn't,** as chez-curl's ci.yml runs its
  own as a step and its `make test` doesn't. The costs, each way:
  - **inside `make test`:** about 7 s more a run, the review measured here: `test-native` on the
    control and the mutant, `test-conventions` twice, and the copy. And it would run inside each
    of `check-test-fails`' 15 or so `make test` cases, each under `TEST_TIMEOUT=5` and a 70 s bound
    (`tests/check-test-fails.sh`, `suite_timeout` and `make_timeout`), where `test-native` alone
    would meet the 5 s, and where its output must never match `judge`'s
    `^(check-suites|test): `. Every lane would run it, and so would the Mac's `make test`;
  - **as CI's step:** about 7 s once a run, in `main` alone. Its cost is three edits slice 2 owns:
    the `main` job's "Checks and suites" run line gains `check-variadic` after `check-test-fails`;
    `tests/check-ci.sh`'s `MAKELINE` for that step gains it; `tests/test-check-ci.sps`' copy of
    the line moves with it (ADR-0005, amended). The Mac step runs `make check-variadic` by hand.

  The step wins: the 5 s and 70 s bounds would need raising or special-casing for a check that
  bites only on Apple arm64, which CI never runs.
- **`test-native` holds the binding by behaviour:** each op's round trip through the binding on an
  open handle, a sentinel per call, and an unknown op answering 1 with the cell untouched. On a
  library without `sqlite3_load_extension`, `ENABLE_LOAD_EXTENSION`'s round trip is named
  unavailable, since Apple's answers 21 to it; the other three run everywhere.

### 4.3 The opt-in and the named condition (ADR-0021, decisions 5 and 10; ADR-0012, ADR-0013, amended)

- **Checked before anything opens.** The refusals' order (ADR-0018, amended in M3 slice 5) gains
  a fifth step after the list's own rules: `(enable-load-extension . #t)` where native's load
  found no `sqlite3_load_extension` raises `&sqlite-extensions-unavailable` from the verb called,
  in the checks' critical section, caught there and raised after it, as the checks' refusals are.
  Nothing is allocated; no `sqlite3_open_v2` and no `sqlite3_db_config` is made.
- **Native records the entry point at its load,** as an exported boolean,
  `load-extension-available?`, computed by `foreign-entry?` in the same step as the required
  ones. A process loads one SQLite (ADR-0002's M1 slice 2 amendment).
- **Otherwise `#t` is a set,** by §4.1, and the record holds the opt-in, fixed when the record is
  made, from the plan, before any setting runs, as the cache's capacity is. A set that fails or
  mismatches closes the connection, so no caller holds a record that says opted in where the C
  call is off. `#f` and no setting make no call, and the record holds no opt-in (Q15).
- **`&sqlite-extensions-unavailable`:** under `&chez-sqlite3-error`, no field beyond its `&who`, a
  fixed `&message`; neither a `&sqlite-error`, since SQLite answered no code, nor a
  `&sqlite-library-unavailable`, since the library loads and works.
- **The decoy** (Q4) gains the three entry points, and a switch for each. **Its open always
  fails** (`SQLITE_CANTOPEN`), so its log can never show a `db_config` call: "no
  `sqlite3_db_config` in the log" passes whatever the code does. What a row can see is whether
  the open was tried, `sqlite3_open_v2` in the log, and that is what the opt-in's rows assert:
  - **`DECOY_LACKS_sqlite3_load_extension`, slice 2:** the load succeeds, with no `missing-api`,
    and `load-extension-available?` is `#f`. A library that lacks an optional entry point loads;
  - **the same build, slice 3:** `open-database ":memory:" '((enable-load-extension . #t))` raises
    the condition, who `open-database`, the log holding the load's entries and no
    `sqlite3_open_v2`; the same through `call-with-database`, whose procedure is never called;
  - **its control, the decoy with the entry point, slice 3:** the same open is tried, and answers
    `&sqlite-error` `cantopen`, with `sqlite3_open_v2` in the log. So the condition is the entry
    point's doing;
  - **`(enable-load-extension . #f)` on the lacking build, slice 3:** the open is tried, with
    `sqlite3_open_v2` in the log, and answers `cantopen` (Q15);
  - **`DECOY_LACKS_sqlite3_db_config` and `DECOY_LACKS_sqlite3_free`, slice 2:** `missing-api`,
    naming each, dealt by the pattern of five (§4.6).

  The decoy's `sqlite3_db_config` is defined variadic, as the header declares it, reads its two
  variadic arguments with `va_arg` and logs them. No row reaches it: it exists because native
  binds it.

### 4.4 `load-extension!` (ADR-0021, decisions 6 to 9)

```scheme
;; load-extension! : (case-> (Database String -> Void) (Database String String -> Void))
```

- **Its checks, in order, before anything reaches C,** each refusal naming `load-extension!`:
  1. a database, else an assertion violation, `not-a-database`;
  2. on its owning thread, else `&sqlite-wrong-thread` (ADR-0010). SQLite itself loads from any
     thread (L5). `call-with-open-handle`, which the call goes through, checks the owner again,
     before its section, so this check and that one both keep another thread out, and the verb's
     own check is what makes the refusal come before the argument checks below;
  3. open, else `&sqlite-closed`;
  4. the path a string, holding no U+0000, and absolute (Q16), else an assertion violation naming
     the string by its kind;
  5. the entry point, when given, a string holding no U+0000;
  6. the opt-in, else an assertion violation, `extension-loading-not-enabled`, whose message
     names the fix, `(enable-load-extension . #t)` (§3, the re-check). On Ubuntu's library this
     check is all that stops a load: the C call is on from the open (pre-work Q3).
- **The call holds a claim,** made by its first expression, as the conveniences' do (ADR-0016,
  amended in M3 slice 3): its one section claims position 0, so a run the call has passed loads
  nothing and raises `&sqlite-closed`. Every load runs the extension's init again (L4); without
  the claim, one remainder resumed twice would run it twice.
- **The one section,** through `call-with-open-handle`, holds:
  - the path's C string, the entry point's or NULL, and the message's slot by
    `call-with-out-pointer`;
  - the connection's extended code, read just before the call, and again just after it;
  - the call;
  - when the slot holds a message, its copy, under a guard, then its `sqlite3_free`, whatever the
    copy did. The copy's outcome is answered as data, and anything it raised is raised after the
    section, so no message is left unfreed on any path;
  - when the extended code changed across the call, the connection's `sqlite3_errmsg`, copied.

  It answers the code and the messages as data; the raise comes after it (ADR-0012, amended).
  Every block lives whole in the section (ADR-0011, amended).
- **A failure** raises `&sqlite-error` whose code and extended code are the call's own answer,
  never `sqlite3_extended_errcode`'s: after rv1's replacing load the connection's code was 5, where
  the call answered 1 (rv1, part B; L8). Its message:
  - **the slot's text, as SQLite wrote it,** which names the path SQLite tried last, with the
    suffix appended when the path failed (L2). SQLite's own failures set no error on the
    connection: on a fresh one it stayed 0, "not an error" (L3), and after an earlier prepare's
    failure it stayed 1, "no such column: nosuch", through a failed load and a successful one
    (rv1, part A). By the source, `sqlite3_load_extension` sets one only when memory runs out;
  - **followed by the connection's message when its extended code changed across the call:** an
    init that fails a call of its own leaves that call's error on the connection, and the slot
    says only "error during initialization: ". rv1's part B, a replacing load beside a held row,
    had the connection at 100, then 5, "unable to delete/modify user-function due to active
    statements": the reason, which the slot lost. The message is then
    "error during initialization: unable to delete/modify user-function due to active
    statements". An init whose failing call leaves the code it found gives the slot's text
    alone;
  - **`sqlite3_errstr`'s,** when the slot holds none.

  No SQL and no offset (ADR-0013, amended). Rows assert the code alone, never the message.
- **No entry point given** passes NULL: SQLite tries `sqlite3_extension_init`, then
  `sqlite3_<letters of the file's base name>_init` (L2). The docs say so.
- **What a load does to the connection:** what the extension registers is the connection's; it
  stays loaded until the close, which unloads it (L4). An init that replaces functions fails while
  a statement of the connection is at a row, and with none held it expires every statement, the
  cache's among them, which re-prepare at their next step (L8). No refusal is added for it:
  SQLite's own failure is raised, with its reason (above), and no promise of ours breaks.
- **`__collect_safe`** (ADR-0011, amended): on a FIFO the call waited for a writer (L6), and a
  plain binding held another thread's collection 1.15 s, the whole wait, where `__collect_safe`
  let it finish in 1 ms (X1).
- **The suites' extension** is `tests/extension.c`, compiled at test time with `$CC -shared
  -fPIC` against the lane's `sqlite3ext.h`, in 50 ms (X1), as `tests/decoy-libsqlite3.c` is
  compiled: the compiler is a test oracle, and a missing compiler or header fails the suite,
  never skips it (ADR-0001, decision 3). `sqlite3ext.h` is in Guix's profile and in every build of
  `build-sqlite.sh`; Ubuntu's `libsqlite3-dev` ships it beside `sqlite3.h` (not read on CI here:
  slice 4's first CI run shows it). Its variants are research's `ext.c`'s: the default init, a
  named one, the derived name, and an init that fails with a message; its functions,
  `chez_half` and `chez_inits`, show that a load took and how many inits ran. On the Mac it is
  compiled as a `.dylib`, and SQLite's retry there appends `.dylib`, not `.so`.

```markdown
- **Decision 3's allowlist gains four of SQLite's, set by `sqlite3_db_config`, not SQL,** named
  by the maintainer's Q14 (2026-11-17, "The rule's names"):

  | Setting | Scheme value | Written as | Read back as |
  |---|---|---|---|
  | `enable-load-extension` | `#t` or `#f` | `1` to `SQLITE_DBCONFIG_ENABLE_LOAD_EXTENSION`, for `#t` alone | the call's cell |
  | `defensive` | `#t` or `#f` | `1` or `0` to `SQLITE_DBCONFIG_DEFENSIVE` | the call's cell |
  | `dqs-dml` | `#t` or `#f` | `1` or `0` to `SQLITE_DBCONFIG_DQS_DML` | the call's cell |
  | `dqs-ddl` | `#t` or `#f` | `1` or `0` to `SQLITE_DBCONFIG_DQS_DDL` | the call's cell |

  `(enable-load-extension . #f)` makes no call, the same as leaving it out (Q15, "Same as
  leaving it out"): the setting says whether `load-extension!` works, and the C flag's own state
  can't be observed through the library.
- **Decision 4's read-back, for these four, is the set's own answer:** one call, no second
  statement. A cell other than the value written raises `&sqlite-setting-mismatch`, its actual
  `()` for a cell the call left at its sentinel; a code but 0 raises `&sqlite-error`, its code
  that answer, never the connection's, and its message `sqlite3_errstr`'s.
- **Decision 5's order holds them:** `busy-timeout` first, the rest in the list's order. Each is
  one call, in a section of its own, which claims the call's claim (amended in M3 slice 5). A set
  does no I/O and never waited, under another's exclusive lock (M4's research, D4).
- **Decision 6 holds them at open alone.** A set that changes a flag expires the connection's
  statements, and one prepared under DQS on fails at its next step once DQS is off (D1, D2). At
  open the connection holds none.
- **Decision 8 holds for them:** a connection opened without one keeps its library's start,
  `DEFENSIVE` 1 on Apple's alone, `ENABLE_LOAD_EXTENSION` 1 on Ubuntu's (M4's pre-work).
- **The refusals' order gains a fifth step,** after the list's own rules: an opt-in on a library
  without `sqlite3_load_extension` raises `&sqlite-extensions-unavailable`.
- **The complement grows:** every other `SQLITE_DBCONFIG_*` op of 3.45.1's and 3.54.1's headers,
  named by ADR-0021's rule, is `unknown-setting`. `trusted-schema` stays this record's PRAGMA, the
  one way in to that flag (Q7).
- **The engine rows** sweep an open holding the four among the six PRAGMAs until it completes
  unexpired, and interleave one remainder's runs, as M3 slice 5's did; each set is made once a
  call.
```

```markdown
## `db_config` and extensions *(provisional)*

- **A connection starts as its library starts it.** No op is set unasked: DQS is on in every
  library measured, `DEFENSIVE` on Apple's alone, `ENABLE_LOAD_EXTENSION` on Ubuntu's (ADR-0021,
  decision 2).

  answer.** Its cell holds a sentinel, neither 0 nor 1, before the call. Code 0 and the value
  written match; another cell raises `&sqlite-setting-mismatch`; another code raises
  `&sqlite-error`, its code that answer and its message `sqlite3_errstr`'s, never the
  connection's, since `db_config` sets no error there. The connection is closed first (ADR-0021,
  decision 3).
- **The opt-in is checked before anything opens:** on a library without
  `sqlite3_load_extension`, `&sqlite-extensions-unavailable`, and no C call (ADR-0021, decision 5).
- **The guarantee lives in Scheme.** `(enable-load-extension . #t)` lets `load-extension!` work;
  `#f`, or no setting, makes it refuse, an assertion violation naming the setting, before anything
  reaches C. Where a library opens connections with the C call on, as Ubuntu's does, that refusal
  is all that stops a load (ADR-0021, decisions 5 and 6).
- **`load-extension!` checks a database, the owning thread, an open connection, an absolute path,
  its entry point, then the opt-in.** It holds a claim. One section makes the call, reads the

  `sqlite3_free` on every path. A failure raises `&sqlite-error` whose code is the call's answer,
  with the slot's message, followed by the connection's when its code changed across the call
  (ADR-0021, decision 7).
- **Never bound:** `sqlite3_enable_load_extension`, `db_config`'s other shapes, `TRUSTED_SCHEMA`
  as an op, `sqlite3_auto_extension` and its siblings (ADR-0021, decision 11).
- **A suite's rows for what a library may lack** are chosen by what the library reports:
  FTS5 by `sqlite-compile-option? "ENABLE_FTS5"`, held to `pragma_module_list`; extension
  loading by native's record of `sqlite3_load_extension`. The rest are named unavailable, never
  silently, and the refusal is asserted in their place, so each suite runs on every lane. The
  `current` lane compiles with `ENABLE_FTS5`, the `floor` lane with SQLite's defaults (ADR-0003,
```

### 10.12 `.plans/traps.md`

Owed with the rest, at the end of "## SQLite", each ending "(M4's research, chez-sqlite3)":

```markdown
- **`db_config` sets no error on its connection, and a load none of its own.** After
  `sqlite3_db_config` answered 1 for an op it didn't know, the connection still said 1, "no such
  column: nosuch", an earlier prepare's, and on a fresh connection 0, which `raise-sqlite-error`
  refuses as no error. After a failed `sqlite3_load_extension`, it still said what it said
  before: the load's text is in its message slot alone. But an extension's init that fails a
  call of its own leaves that call's error there: a replacing load beside a held row answered 1,
  its slot said "error during initialization: ", and the connection said 5, "unable to
  delete/modify user-function due to active statements" (M4's research, D3, L3; M4's plan
  review, rv1, rv2). Take the code from the call's answer. (M4's research, chez-sqlite3)
- **A failed load names a path the caller never gave.** SQLite tries the path, then the path with
  a suffix appended, `.so` on Linux and `.dylib` under `__APPLE__` (3.45.1's `azEndings`), and
  reports the second failure. On Linux a missing `nosuch.so` read
  `nosuch.so.so: cannot open shared object file`, and so did an empty file or a directory,
  hiding the real cause (L2). (M4's research, chez-sqlite3)
- **A bare name to `sqlite3_load_extension` is `dlopen`'s search.** On Linux, `ext.so`, with the
  working directory holding it, wasn't found, and `./ext.so` was (L2); from another working
  directory, `ext.so` and `ext` both loaded with `LD_LIBRARY_PATH` naming the directory that held
  it, and neither without it (M4's plan review, rv3). macOS's dlopen(3) documents a leaf name
  searched in the working directory too, for an unrestricted process: not measured.
  (M4's research, chez-sqlite3)
- **A `db_config` set that changes a flag expires every statement on its connection;** one that
  changes nothing doesn't. A statement prepared and run with DQS on failed at its next step once
  `DQS_DML` was turned off: its re-prepare refused the double-quoted name (D1, D2). (M4's
  research, chez-sqlite3)
- **Each library opens connections its own way.** Ubuntu's 3.45.1, built
  `ENABLE_LOAD_EXTENSION`, opens every connection with the C call to `sqlite3_load_extension`
  on; the others whose start could be read open it off. Apple's answers 21 to the op and leaves
  the cell, so its start isn't known. Apple's 3.51.0 opens every connection with `DEFENSIVE`
  on, and no compile option it lists says so (M4's pre-work). (M4's research, chez-sqlite3)
- **`DEFENSIVE` turns `writable_schema` off without a word.** Under it,
  `PRAGMA writable_schema = 1` answered done, and read back 0 (M4's pre-work). (M4's research,
  chez-sqlite3)
- **An FTS5 table on a library without FTS5 fails at its step, not its prepare:** "no such
  module: fts5", 1 (M4's pre-work; F1). (M4's research, chez-sqlite3)
- **Every load runs the extension's init again, and a close unloads it.** Its init count read 1,
  2 and 3 across two loads into one connection and one into another, and 1 again once both had
  closed. A load whose init replaces a function failed while a statement of the connection was at
  a row, and with none held it expired every statement (L4, L8). (M4's research, chez-sqlite3)
```

## Amendment, 2026-11-18: a start can't see a set that writes it (M4 slice 3)

Accepted by the maintainer on 2026-11-18 ("Accept all"), and its additions after the M4 session's check the same day ("Accept all"), proposed in M4 slice 3, from its review (Opus) ([the slice's log](m4-slice-3-mutation-log.md)).

- **§4.7's "an op set unasked" holds only half its claim.** A start row sees a plant that moves an
  op off its start. It can't see a plant that writes the start value, such as `defensive` set to 0
  where it starts at 0, or `dqs-dml` set to 1 where it starts at 1 (the review's R1 and R2). Nor
  can it see a set that is skipped where the value asked is the start (R6).
- **Slice 3 holds both directions** by moving every op off the library's start first, through an
  `sqlite3_auto_extension` entry point, then reading `open-database`'s connection
  ([ADR-0021](decisions/0021-db-config-options-and-extension-loading.md), amended 2026-11-18).
- **Every list shape a plant can key on is judged over moved starts,** not only the empty and
  single-op lists. A plant that set `dqs-dml` to 1 whenever a PRAGMA was in the list passed until
  the multi-setting lists were judged too (the M4 session's check, its M1).
- **An expected value never comes from what the code under test writes,** the suite's own helper
  included. The moves are held to 1 minus the start, read on their own; an entry point that moved
  each op to its start passed while the expected values came from its own list (the check's M2).
- **Slice 4's rows** check a plant against a moved start the same way, wherever a start could
  equal the value planted.
